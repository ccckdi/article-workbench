# 文章工作台

AI 全栈开发考核起始工程 · v0.3.0

开发工具、AI 工具和实现方案自由选择。

## 业务背景

一个内容团队维护面向新成员的办事指南。作者和编辑共同更新文章，内容负责人审核并发布。团队既要避免编辑覆盖、误发布，也要知道哪些内容真正帮助读者完成事情。

下一个迭代只有 8 个编辑工时，最多能改进 3 篇文章。负责人希望优先减少读者看完指南后仍需人工解释的问题。现有资料包括文章快照、阅读事件、读者反馈和人工咨询记录，数据来自不同导出批次，完整性与可靠性并不一致。请交付一个可运行的系统，支持文章协作审核、内容效果分析和改进决策，并把选定的改进带回文章修订流程。

工程已有登录、角色、文章编辑、发布、公开阅读和持久化能力。当前可以直接发布，保存已发布文章会改变公开内容，旧编辑会覆盖新修改。正式提交、审核、版本保护、冲突处理、操作追溯、数据采集与导入、分析和改进决策由你完成。

可以调整工程结构、语言与框架，保留完整业务流程。使用公开资料和开源代码时注明来源及必要的许可证信息。

## 业务要求

- **R1 写作与提交**：作者可以保存草稿、正式提交、查看待审核与处理结果。草稿与正式提交应清楚区分。退回必须带有意见，作者可以修改后再次提交。作者和编辑应能辨认当前内容、处理进度和待处理事项。
- **R2 人工审核与权限**：审核人员可以查看提交内容并作出通过或退回决定；发布人员可以发布或取消发布。普通作者不得审核或发布。审核者与发布者可以是同一人。权限限制由服务端执行，审核时能够辨认本次提交的内容及相对上一已发布内容的主要变化；首次提交明确显示为首次发布。
- **R3 可信发布**：首次发布和后续更新都必须对应人工通过的内容。标题、正文和公开摘要不得泄露未审核修改。修改已发布文章时，原已发布内容继续可见，直到新内容获批并被授权发布，或文章被授权取消发布。不能悄然改变正在审核的内容，也不能把旧批准用于新修改。
- **R4 多人编辑**：作者与编辑可以先后编辑同一篇文章。两人基于旧内容保存时，不得静默覆盖已保存的工作。冲突发生后，应保留当前用户的输入，提供能够辨认相关版本和变化的信息，以及可理解、可继续操作的处理方式。无需实时协同、自动合并或完整 Git 功能。
- **R5 操作追溯**：从文章中可以查询关键修改、提交、审核、发布和取消发布记录，辨认操作者、时间、内容版本、结果和意见。普通作者不能伪造或修改记录。重复点击、请求重试以及审核、发布与修改同时发生时，结果应可解释，不产生重复生效或错误发布。
- **R6 工程交付**：提供实际运行的前后端、持久化数据和必要测试。交付说明包含启动、验证、部署和数据恢复方法。重启后能继续处理文章、查看分析结果及改进计划。根据实际数据变更说明处理方式。
- **R7 数据收集与处理**：支持导入附件中的历史数据，并在公开阅读页采集新的阅读访问和“有帮助／没有帮助”反馈。新采集的数据能够进入分析，并辨认对应的文章与已发布内容。保留可追溯的数据来源和处理结果；重复导入或重复上报不能让统计无故增加。发现重复、缺失、无效、迟到或可疑数据时，选择合理的处理方式，并让负责人看到哪些数据可用、哪些受限以及原因。历史数据与演示中新产生的数据应能分别查看，匿名标识不得当作真实人数或用于识别个人。
- **R8 分析与改进决策**：为内容负责人提供实际使用数据的分析页面，支持按时间和来源渠道查看文章表现，并回查支撑结论的数据或明细。自行确定评价内容效果的指标，明确业务含义、统计范围、分子分母和限制。结合阅读、反馈、人工咨询及编辑成本，提出不超过 3 篇、合计不超过 8 个编辑工时的改进计划，说明选了什么、暂缓了什么、证据与代价，以及哪些结论仍需补充验证。负责人可以调整选择并保存计划，不能把未知或缺失数据展示为确定的好坏结论。能够从计划中的文章新建或关联修订草稿，经同一审核发布流程完成一次改进，并查看其处理进度；同一次关联操作重试不能重复创建修订稿。

## 协作边界

| 角色 | 业务范围 |
| --- | --- |
| 作者 | 查看、编辑和提交自己的文章，包括编辑修改后的内容；查看自己文章的处理记录 |
| 编辑 | 查看、编辑和提交团队文章；查看团队文章的处理记录 |
| 审核人员 | 查看团队文章、提交内容和处理记录；通过或退回提交 |
| 发布人员 | 查看团队文章、批准依据和处理记录；发布或取消发布 |
| 内容负责人（manager） | 具备编辑、审核、发布权限；导入数据、查看分析、调整和保存改进计划 |
| 未登录读者 | 阅读已发布文章，提交阅读反馈；不得访问非公开文章、内部分析、原始明细或改进计划 |

其他测试账号无权访问内部分析、原始明细和改进计划。公开采集接口只接受当前已发布文章的阅读或反馈信息，不能写入审批、发布或计划结果。可以自行决定反馈频率和防重复规则，说明匿名采集的可靠性边界。

取消发布不会自动抹去原批准依据；内容及批准仍有效时，可由发布人员再次发布。内容发生变化时，修改后的内容必须重新审核。文章在送审后如何继续编辑、如何认定提交失效以及如何处理冲突，由你设计并保持交互与服务端行为一致。

数据资料中的历史文章快照用于分析，历史发布信息不能代替本系统的批准。从历史文章创建修订稿时保留来源关联，并按同一流程提交、审核和发布。支持手工选择或基于规则推荐，不要求模型调用、复杂推荐算法或自动生成正文。

本题内容范围为普通文章的标题、正文和摘要，以及上述数据与改进计划。不要求新增分类、标签、附件、评论、定时发布、外部审批或多级流程。

## 业务场景

文章 A 已发布，作者将其修改成 B。B 保存、提交、退回修改和重新审核期间，读者继续看到 A；B 获批并被授权发布后，读者才看到 B。审核人员能够确认自己处理的是哪份内容。另一位编辑从旧页面保存时，不能覆盖已保存的修改。

负责人准备安排下一轮内容改进。某篇文章访问量高，可能受活动流量或自动访问影响；某篇文章反馈比例好，可能只有少量反馈；咨询数量变化也可能由接触人群和记录方式造成。你需要从实际数据中判断哪些证据足以支持行动，哪些只能作为待验证的线索，并在预算内作出选择。结论不要求唯一，但计算过程和选择依据必须能够复核。

## 数据资料

`fixtures/content-operations/` 包含 8 篇历史文章、两个批次的阅读事件、读者反馈和人工咨询记录，均为合成数据。数据字典说明字段、导出范围和业务口径，未提供清洗程序、指标结果、排行榜或参考决策。

历史分析期间固定为北京时间 2026-08-01 00:00 至 2026-08-15 00:00，右端不包含；导出截止北京时间 2026-08-17 00:00。时间筛选以事件发生时间为基础，迟到数据的纳入方式由你说明。两个批次可能重叠，不能默认每行都是独立行为。阅读时长、滚动深度和主动反馈都是观察信号，不能直接证明读者完成了办事任务。

编辑工时采用文章资料中的估算值。同一篇文章在计划中只计一次，不要求把预算用满。若认为估算或现有数据不足，可以明确假设与后续验证安排；当前计划仍须按给定估算满足预算。

## 启动

准备 JDK 21、Node.js 24（至少 24.11.0，含 Corepack）。在项目目录执行：

```sh
cd ui
corepack pnpm install --frozen-lockfile
corepack pnpm build
cd ..
./gradlew :backend:bootRun
```

访问 http://localhost:8090 ，工作台为 http://localhost:8090/console/ 。初次启动自动初始化演示数据。Windows 使用 `gradlew.bat`。

首次安装会下载构建工具和依赖，无需另外安装数据库或获取其他业务工程。


默认数据目录为运行目录下的 `data`，使用 H2 文件数据库。开发启动与在项目目录运行 JAR 时使用同一数据目录。账号、文章在重启后保留，会话失效后重新登录。

```text
backend/
  src/main/java/dev/workbench/   接口、认证、业务服务、数据库访问

  src/test/                     后端测试
ui/
  src/views/                    登录、列表、编辑
  src/components/               Vue 公共组件
  src/stores/                   Pinia 认证状态
  src/utils/                    日期工具
  tests/                        单元测试、浏览器测试
fixtures/content-operations/   历史业务数据、数据字典和校验清单

```

`ArticleService` 负责文章操作，`ArticleController` 提供接口，`PageController` 提供公开页面。数据库定义在 `backend/src/main/resources/schema.sql`，目前包含 users 和 articles 两张表。

### 现有接口

| 方法与路径                       | 用途                                 |
| -------------------------------- | ------------------------------------ |
| GET /api/health                  | 服务及数据库检查                     |
| GET /api/csrf                    | 获取写请求使用的 CSRF token          |
| GET /api/session                 | 当前账号                             |
| POST /api/session                | 账号口令登录                         |
| DELETE /api/session              | 退出                                 |
| GET /api/articles                | 按权限查询文章，支持 q、status、page |
| POST /api/articles               | 创建草稿                             |
| GET /api/articles/:id            | 读取文章                             |
| PUT /api/articles/:id            | 保存文章                             |
| POST /api/articles/:id/publish   | 发布                                 |
| POST /api/articles/:id/unpublish | 取消发布                             |
| GET /api/public/articles         | 公开列表                             |
| GET /api/public/articles/:id     | 公开详情                             |

写请求需要保留 Cookie，并携带 `GET /api/csrf` 返回的 headerName 和 token。登录参数为 username、password。创建与保存参数为 title、excerpt、body，长度上限分别为 200、500、50,000 字符。详情返回 `{ article }`，列表返回 `{ items, total, page, size }` 及分页信息。接口和数据结构可随业务实现调整。
